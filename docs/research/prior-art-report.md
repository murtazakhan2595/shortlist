# Port the parts, keep building Shortlist

Others have built much of what Shortlist does, but nobody has built Shortlist. Two very large MIT-licensed projects cover about half of its features on paper: **career-ops (74,441 stars)** and **MadsLorentzen/ai-job-search (46,694 stars)**. Both are draft-only and never send, and both find jobs, score them and write application text. career-ops already has code for Himalayas, Hacker News, Greenhouse, Lever and Ashby. But both are local, file-based toolkits run inside a coding CLI such as Claude Code. Neither has a database, a scheduler on a host, per-step model settings, a spending cap, Gmail draft creation, screenshot capture of LinkedIn posts, or eligibility rules that keep jobs open to Pakistan and drop India. Forking either one would mean replacing its store, its runtime, its user interface and its scheduler, which is most of the system. The commercial tools are US-focused, and the auto-apply bots among them average 2.1 out of 5 on Trustpilot. The YouTube builds are mostly no-code n8n workflows that scrape LinkedIn, which Shortlist rules out. The recommendation is to **build Shortlist as planned and port about ten specific pieces, with attribution**. Those pieces are career-ops's source modules and filter logic, ai-job-search's scoring rubric and fact-checking prompts, and both projects' rules for answering forms. Doing so needs one change to principle 6, a licence rule in sprint 1, and changes to about 15 sprint items, listed at the end of this report. The work saves several days in sprints 2 to 4 and makes stage 2 much cheaper. It also gives the README a clear "prior art" story, which matters because employers are likely to know these two repositories.

## Two viral repositories cover half of Shortlist on paper

**ai-job-search** is a set of Claude Code slash commands and skills. About 11.8k lines of it are Markdown prompts, backed by small Python and TypeScript (Bun) command-line helpers. Its flow is `/setup` (build the profile), `/scrape` (search job sites), `/rank` (score in bulk), then `/apply`. `/apply` assesses fit, asks "Should I proceed with drafting?", drafts a LaTeX CV and cover letter, has a reviewer subagent critique them, revises, and records the application as `drafted` ([apply.md](https://github.com/MadsLorentzen/ai-job-search/blob/master/.claude/commands/apply.md)). It has **no model configuration, no scheduler and no hosting**. All state lives in CSV and JSON files inside the user's fork ([README](https://github.com/MadsLorentzen/ai-job-search/blob/master/README.md)). Its six bundled job-site tools cover Danish boards plus LinkedIn's unauthenticated `jobs-guest` endpoints, and the skill itself admits that "automated access is against LinkedIn's Terms of Service" ([linkedin-search SKILL.md](https://github.com/MadsLorentzen/ai-job-search/blob/master/.agents/skills/linkedin-search/SKILL.md)). Activity peaked in July and August 2026: 123 and 107 commits, and ten releases from v1.0.0 on 22 July. Pace has slowed in October. The author says the tool produced "Sixty-nine tailored applications, twenty first interviews, and one signed contract" ([README](https://github.com/MadsLorentzen/ai-job-search/blob/master/README.md)).

**career-ops** is larger and closer to Shortlist. It has about 105 source modules ("providers"), a Next.js 16 web app, a Go terminal dashboard, an `email` mode, an `apply` mode that "reads form + generates answers", and a golden-set evaluation ([README](https://github.com/career-ops-hq/career-ops)). Its stated limits match Shortlist's principle 1: "The script never POSTs" and "There is no mail transport anywhere in this codebase." Reading the code shows the gaps behind those claims. The web app binds to `127.0.0.1` and "has no login — the bind is the access control" ([web/README.md](https://github.com/career-ops-hq/career-ops/blob/main/web/README.md)). It runs models by starting a coding CLI as a child process ([clis.ts](https://github.com/career-ops-hq/career-ops/blob/main/web/src/lib/clis.ts)). Model choice is a single `spend_tier` per session, not a setting per step ([modes/_shared.md](https://github.com/career-ops-hq/career-ops/blob/main/modes/_shared.md)). Project policy says Markdown files are the "permanent source of truth" and that SQLite "will never become a primary store — not even opt-in" ([ARCHITECTURE.md](https://github.com/career-ops-hq/career-ops/blob/main/ARCHITECTURE.md)).

Shortlist's distinctive features fall almost entirely in the right-hand column. Some of them are also its strongest portfolio material: per-step model routing backed by quality checks per model, a cost cap, a no-send rule enforced in code, and screenshot capture.

## Nothing else found builds Shortlist's Pakistan-specific core

**Other open-source projects split into three groups.** The first is LinkedIn auto-apply bots that drive a browser: GodsScion (2,930 stars), nicolomantini, wodsuz, beatwad, stickerdaniel's LinkedIn MCP server, and the now-defunct AIHawk. Shortlist excludes these by design (principle 3; section 9). The second is draft-only tools from 2026 that confirm the trend Shortlist follows. Gsync/jobsync (1,400 stars, MIT) is the only full TypeScript app among them. It runs Next.js 15, Prisma and the Vercel AI SDK, discovers jobs on Greenhouse, Lever and Ashby, and puts them in an accept-or-dismiss queue ([Gsync/jobsync](https://github.com/Gsync/jobsync)). neonwatty/job-apply-plugin reuses answers with "confirmed / inferred / missing / sensitive" states ([README](https://github.com/neonwatty/job-apply-plugin)). DanielPan12/JobHuntBot ships an `answer_bank.template.md` of "reusable truthful answers" ([README](https://github.com/DanielPan12/JobHuntBot)). The third is the one small project closest to Shortlist's complete loop, **MaxwellVolz/hn_whos_hiring** (MIT, 11 stars). Its README says it scores HN posts from 0 to 100 against "the locations you'll work from, your seniority and your dealbreakers", can "queue it to become a Gmail draft with your resume attached", and does "Form prefill… stops before submit" ([GitHub](https://github.com/MaxwellVolz/hn_whos_hiring)). Its code was not read, so those claims are unverified. It is still the first thing to read before items 2.3 and 7. AIHawk is gone: its old URLs now redirect to `feder-cr/invisible_dots`, an unrelated anti-bot-detection project whose oldest commit is dated 29 September 2026 ([invisible_dots](https://github.com/feder-cr/invisible_dots)).

**Commercial products are US-focused, and the auto-apply group has poor independent reviews.** Jobright says it "focuses on the U.S. market" ([Jobright blog](https://jobright.ai/blog/is-jobright-legit/)), and Nox also targets the US. JobCopilot and LazyApply both score **2.1/5 on Trustpilot**. Complaints include roles below the stated pay floor, irrelevant applications, and "nearly 600 applications and no interviews" ([Trustpilot JobCopilot](https://www.trustpilot.com/review/jobcopilot.com); [Trustpilot LazyApply](https://www.trustpilot.com/review/lazyapply.com)). LoopCV is the only product found that emails recruiters, and it sends those emails itself from templates ([scoutify](https://scoutify.com/blog/loopcv-review/)). No product handles Google Forms, LinkedIn recruiter posts that give an email address, or an eligibility rule open to Pakistan and excluding India. The useful commercial complement is a free autofill copilot. **Huntr's free tier includes unlimited application autofills** ([huntr.co/pricing](https://huntr.co/pricing)), which covers much of what requirement L2, the planned browser extension, would do on ATS forms. Whether it works on Google Forms has not been tested.

**The YouTube examples are mostly n8n workflows built for volume, with their templates behind sign-up or paid gates.** The most-viewed builds scrape LinkedIn through Apify and filter with GPT-4o. Examples are Michele Torti (~144k views, [YouTube](https://www.youtube.com/watch?v=lq8OaM-SeJo)) and Nick Saraev's "apply to 1000+ jobs" (~118k views, the only one that drafts outreach email, with templates in a paid community, [YouTube](https://www.youtube.com/watch?v=ntSbFUQZHJ0)). JavaScript Mastery's JobPilot build (~214k views) is Next.js and public, but it has **no licence** and uses an authenticated LinkedIn session with experimental Easy Apply auto-submit ([adrianhajdin/job_pilot](https://github.com/adrianhajdin/job_pilot)). No video found builds a job agent with LangGraph. Nothing on YouTube is reusable. The genre's push for volume and its reliance on LinkedIn scraping make Shortlist's eligibility-first, human-sends design stand out against it, which helps the portfolio case.

## Forking either project would rewrite most of it

The case for forking career-ops is real. It already avoids terms violations for Shortlist's five target sources. Its maintainer calls `scan.mjs` "zero-token and API-only by design" ([#2286](https://github.com/career-ops-hq/career-ops/issues/2286)), and its contributing guide rejects LinkedIn scraping ([CONTRIBUTING.md](https://github.com/career-ops-hq/career-ops/blob/main/CONTRIBUTING.md)). It is also very active, with **717 PRs merged in the month to 14 October** ([issues](https://github.com/career-ops-hq/career-ops/issues)). That activity is the problem. A fork that swaps the Markdown store for Supabase would split from upstream at once, and the project's policy rules out a primary database, so the change would never be merged back. A fork would also mean carrying about **179k lines of `.mjs` that Shortlist doesn't use**, including a 4,988-line `scan.mjs`. Replacing the local, login-free UI security model and the CLI subprocess runtime touches every model call. ai-job-search is a worse fit. Its runtime is Claude Code itself, its prompts assume Claude Code tools (Read, Agent, WebFetch), and its output is LaTeX PDFs, not emails.

A fork would also undercut two of Shortlist's own goals. Plan section 1 asks that the owner "be able to explain every design decision", which is hard with 180k inherited lines. REQUIREMENTS section 3 sets portfolio criteria that a fork of a 74k-star repository would weaken. Porting specific modules keeps the architecture Shortlist's own and still saves the tedious parts: response shapes, edge cases and test fixtures for each source.

## Ten pieces are worth porting, and several are worth refusing

**Source code (career-ops, MIT).** The five target modules are small, dependency-free JavaScript files checked with `@ts-check`, and each takes an injected fetch function. Their sizes are Himalayas 129 lines, HN 185, Lever 133, Greenhouse 280 and Ashby 538. They come with contract tests under `tests/providers/` ([tests/providers](https://github.com/career-ops-hq/career-ops/tree/main/tests/providers)). The most valuable is `hackernews.mjs`. It finds the thread through Algolia `search_by_date?tags=story,author_whoishiring`, reads it through the item API, and parses comments with `parseHnComment` ([hackernews.mjs](https://github.com/career-ops-hq/career-ops/blob/main/providers/hackernews.mjs)). Next is Ashby's compensation-tier parsing and its `INTERVAL_MULTIPLIERS` annualisation table ([ashby.mjs](https://github.com/career-ops-hq/career-ops/blob/main/providers/ashby.mjs)). After that come Greenhouse slug detection (including embed `?for=`) and Lever's `allLocations` merge with its EU host. The Himalayas module should serve as a shape reference only. It fetches **one page of 50 and drops salary and description** ([himalayas.mjs](https://github.com/career-ops-hq/career-ops/blob/main/providers/himalayas.mjs)). Himalayas' own API offers cursor paging, 20 records per request, `country` and `worldwide` filters, and `minSalary`/`maxSalary`/`salaryPeriod`/`currency` ([Himalayas API](https://himalayas.app/api)). Item 4.1 needs all of those. The career-ops researcher estimates porting the source modules and the location filter to TypeScript with Zod at roughly one to two focused days. That figure is an estimate, not measured.

**Eligibility logic, split between both projects.** career-ops's `compileLocationKeyword` matches on word boundaries, so blocking "India" no longer drops "Indiana". Its tier order is `block_hard` → `always_allow` → `block` → `allow`, and its `country_eligibility_filter` phrase lists are opt-in ([scan.mjs](https://github.com/career-ops-hq/career-ops/blob/main/scan.mjs); [portals.example.yml](https://github.com/career-ops-hq/career-ops/blob/main/templates/portals.example.yml)). Together they make a good deterministic first pass for D3a. ai-job-search's "Eligibility Gate" table supplies the verdict rules. Citizenship or permanent residency is FAIL with the wording quoted, and clearance is FAIL. Silence is PROCEED marked unverified, because "Silence is not permission" ([04-job-evaluation.md](https://github.com/MadsLorentzen/ai-job-search/blob/master/.claude/skills/job-application-assistant/04-job-evaluation.md)). That is D4 and Q4 almost word for word. One behaviour must **not** be ported. career-ops's salary filter rejects any job whose currency differs from the filter's and does no currency conversion ([scan.mjs L1044-1103](https://github.com/career-ops-hq/career-ops/blob/main/scan.mjs)). That would drop every EUR or GBP job and break Q3. Shortlist needs its own pay normaliser that converts to monthly USD and stores the rate's date. Frankfurter (MIT) and fawazahmed0/exchange-api (CC0) can supply the rates ([frankfurter](https://github.com/lineofflight/frankfurter); [exchange-api](https://github.com/fawazahmed0/exchange-api)). Neither project handles D3a's "employer is based in India" case, so that stays an extraction field for the model.

**Prompts and guardrails for writing (ai-job-search, MIT).** Item 2.2 has four parts to take. The first is the grounding audit: every date, employer, title and metric must be supported by the profile sources, or it is removed. The second is the "write new facts back to the profile" rule, which matches F5. The third is the reviewer's output contract. Part A is JSON edits with `old_string`/`new_string`/`reason`, and Part B is four required critique categories in which "no issues" must be stated explicitly ([apply.md](https://github.com/MadsLorentzen/ai-job-search/blob/master/.claude/commands/apply.md)). The fourth is the writing-style file: a banned-phrase list ("I am passionate about", "hit the ground running") and the **interview backtrack test** ([03-writing-style.md](https://github.com/MadsLorentzen/ai-job-search/blob/master/.claude/skills/job-application-assistant/03-writing-style.md)). A contributor called the drafter-reviewer split "the gem" and said the backtrack test killed "more than one tempting stretch" ([Issue #19](https://github.com/MadsLorentzen/ai-job-search/issues/19)). career-ops adds a deterministic layer in `verify-cv-facts.mjs`. It extracts numbers and tool names from generated text, rejects any not found in the source CV, and checks a configurable list of forbidden phrases ([verify-cv-facts.mjs](https://github.com/career-ops-hq/career-ops/blob/main/verify-cv-facts.mjs)). Take the approach, not the 142 KB file. Running a cheap check in code before the model's check is the right shape for X4.

**Form-answering rules (career-ops and neonwatty).** career-ops's `apply` mode forbids inventing answers for "legal, demographic, work-authorization, visa/sponsorship, salary, disability, veteran, background-check, relocation, or self-identification fields". When a sensitive answer is missing it marks the field `needs_candidate_confirmation`. It also says "A missing limit is never proof that an answer fits" ([modes/apply.md](https://github.com/career-ops-hq/career-ops/blob/main/modes/apply.md)). neonwatty's four provenance states give the answer bank a way to say why it trusts each answer. ai-job-search's `08-application-forms.md` sets field sizes: a 100–200-word self-introduction, and project entries of 100–150 words each with a ~60-word short version ([08-application-forms.md](https://github.com/MadsLorentzen/ai-job-search/blob/master/.claude/skills/job-application-assistant/08-application-forms.md)). Those sizes are a ready template for sprint 0's answer bank.

**Scoring, evaluation and data seeds.** ai-job-search's rubric weights Technical 30%, Experience 25%, Behavioural 15% and Career Alignment 30%, with Location as pass or fail. It gives bands from Strong (75+) to Poor (<30), and says to "Match on the function... not the literal job title". `/rank` stores one to three strengths and gaps verbatim and never scores from the title alone ([rank.md](https://github.com/MadsLorentzen/ai-job-search/blob/master/.claude/commands/rank.md)). `job_key.py` builds a deterministic company, title and URL key, with a SHA-1 fallback for non-Latin names ([job_key.py](https://github.com/MadsLorentzen/ai-job-search/blob/master/tools/job_key.py)). It ports directly to the `listings` fingerprint. career-ops's evaluation design suits item 1.6: frozen reference labels, replayed fixtures, and an agreement gate with archetype agreement ≥0.8 and score within ±0.5 ([evals/README.md](https://github.com/career-ops-hq/career-ops/blob/main/evals/README.md)). promptfoo (MIT, TypeScript, 25,990 stars) can run the cases per model instead of a hand-written runner ([promptfoo](https://github.com/promptfoo/promptfoo)). For stage 2, **Feashliaa/job-board-aggregator (MIT, updated daily)** ships plain JSON lists of 8,333 Greenhouse tokens, 4,368 Lever slugs and 3,161 Ashby boards ([GitHub](https://github.com/Feashliaa/job-board-aggregator)). These can seed the D8 watchlist, as long as each slug is re-checked against its endpoint before use. ai-job-search's `/gmail-sync` query (`newer_than:30d -in:sent -in:drafts` plus ATS sender domains) and its email-classification table can be reused for sprint 9 and L1 ([gmail-sync.md](https://github.com/MadsLorentzen/ai-job-search/blob/master/.claude/commands/gmail-sync.md)).

**The supporting TypeScript packages are maintained.** For Gmail, use `@googleapis/gmail` (Apache-2.0) with nodemailer's MailComposer in build-only mode (MIT-0), then `drafts.create` with `{message:{raw}}` ([Gmail drafts guide](https://developers.google.com/workspace/gmail/api/guides/drafts)). For the PWA, use `@serwist/next`, because **`next-pwa` has had no release since 2022** ([serwist](https://github.com/serwist/serwist); [next-pwa](https://github.com/shadowwalker/next-pwa)). For LangGraph state, `@langchain/langgraph-checkpoint-postgres` 1.1.0 (MIT) was released on 12 October 2026 ([langgraphjs](https://github.com/langchain-ai/langgraphjs)). No example combines it with Supabase, so plan to run it in its own schema through a session-pooler or direct connection.

**Four things to refuse.** First, ai-job-search's LinkedIn guest-endpoint scraper. Second, career-ops's DuckDuckGo HTML search fallback ([scan.mjs](https://github.com/career-ops-hq/career-ops/blob/main/scan.mjs)). Third, career-ops's rule for admitting new sources, which checks robots.txt only and sets aside AI-crawler rules. It records ITviec and CareerViet as precedents, "both carrying disallows they route around" ([CONTRIBUTING.md](https://github.com/career-ops-hq/career-ops/blob/main/CONTRIBUTING.md)). That conflicts with principle 3, which requires reading each source's terms. Fourth, JobSpy and its TypeScript ports, which scrape LinkedIn and Indeed.

## Licences allow porting, but principle 6 needs one more sentence

The projects worth taking from are permissively licensed. Each licence covers the projects' prompts as well as their code, since the prompts are files in the repository. **ai-job-search** is MIT, © 2026 Mads Lorentzen ([LICENSE](https://github.com/MadsLorentzen/ai-job-search/blob/master/LICENSE)). **career-ops** is MIT, © 2026 Santiago Fernández de Valderrama, with no contributor agreement ([LICENSE](https://github.com/career-ops-hq/career-ops/blob/main/LICENSE)). JobSync, MaxwellVolz, neonwatty, JobHuntBot, Feashliaa and promptfoo are also MIT. googleapis is Apache-2.0, nodemailer is MIT-0 and pgmq uses the PostgreSQL licence. Keeping the copyright notice is enough. Two policies outside the licences apply. career-ops's trademark policy reserves the name, so calling Shortlist "based on career-ops" is fine but the name itself is not ([TRADEMARK.md](https://github.com/career-ops-hq/career-ops/blob/main/TRADEMARK.md)). ai-job-search's "Pip" mascot derives from Anthropic's Claude Code mascot and should not be copied ([Issue #48](https://github.com/MadsLorentzen/ai-job-search/issues/48)).

Several projects must not be copied from. **AGPL-3.0**: olyaiy/resume-lm (the only Next.js plus Supabase project found, now archived), offerPilot, and later AIHawk forks. **Commons Clause**: DaKheera47/job-ops, which forbids selling. **No licence, so all rights reserved**: adrianhajdin/job_pilot, mayankjoshii/claude-job-skill, Anshul439/job-auto-apply, borgius/jobspy-mcp-server, yanirs/established-remote, lukasz-madon/awesome-remote-job and the Remotive docs repository. **GPL-3.0**: brmeyer's HN parser. **ODbL share-alike**: mledoze/countries. The licences were read from GitHub's API for each repository ([resume-lm](https://github.com/olyaiy/resume-lm); [job-ops LICENSE](https://github.com/DaKheera47/job-ops/blob/main/LICENSE); [established-remote](https://github.com/yanirs/established-remote); [mledoze/countries](https://github.com/mledoze/countries)). Shortlist is private and non-commercial today, but sprint 6 publishes it, and AGPL obligations apply once code is shared. The safe rule is an allowlist, not a judgement made case by case.

REQUIREMENTS principle 6 says "Written from scratch, with no code, prompts or data from any employer." "From scratch" sits awkwardly next to porting someone else's code, so the principle should state the open-source exception outright. The other risks are practical. **Ported code carries upstream bugs.** ai-job-search has an open bug where "A failed fetch is treated as `expired`, and `expired` is never retried" ([Issues](https://github.com/MadsLorentzen/ai-job-search/issues)), and a fork maintainer admitted to "three fail-open holes" in a robots checker ([Discussion #78](https://github.com/MadsLorentzen/ai-job-search/discussions/78)). Pin a commit, port the tests along with the code, and re-check every endpoint live. **Personal data leaks** happened in ai-job-search. `gh repo fork --clone` set upstream as the default remote, so users' agents filed their application data as public issues ([Issue #389](https://github.com/MadsLorentzen/ai-job-search/issues/389)). resume-lm shipped Supabase's demo service-role keys as fallbacks ([olyaiy/resume-lm](https://github.com/olyaiy/resume-lm)). career-ops's Gmail plugin never requests a scope; it gets whatever the refresh token carries ([plugins/gmail/index.mjs](https://github.com/career-ops-hq/career-ops/blob/main/plugins/gmail/index.mjs)). That is a quiet way for a no-send guarantee to fail. Finally, the name "Shortlist" clashes with MLS-Tech-Inc/shortlistjobs-mcp (37 stars). This matters only for search results, not legally.

## Conclusion and plan changes

The research changes what Shortlist's portfolio story should be. "An AI agent that finds jobs and drafts applications" is now a 74k-star commodity. What no one has shipped is the engineering around it: a hosted, single-owner system where each step's model is chosen by measured quality and cost, spending stops at a cap, sending is impossible by construction, and eligibility rules come from a non-US candidate's real situation. The README should lead with that comparison against prior art, not hide from it. A second point deserves attention. Both viral authors report landing a job after roughly 70 applications in total, though career-ops's figures conflict between sources. Shortlist plans a daily list of found jobs, and the independent reviews of high-volume bots are poor. The reply-rate data from Q11 and U5 should be allowed to lower N, not only raise it. In plan order, these are the specific changes:
